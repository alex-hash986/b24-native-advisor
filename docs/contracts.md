# Контракты v1

Исполняемые DTO определены в [core/contracts.py](../core/contracts.py). Все модели наследуют Pydantic v2 `ConfigDict(extra="forbid")`. Идентификаторы запросов и слепков — UUID. Временные метки требуют часового пояса, при сохранении нормализуются к UTC. Область `tenant_id` + `portal_id` определяется доверенной конфигурацией приложения. Текст вопроса и вывод модели не задают область доступа.

| DTO | Содержание |
| --- | --- |
| `SnapshotRequest` | Область, ID запроса и непустое множество запрошенных областей аудита |
| `PortalSnapshot` | Область, ID запроса и слепка, время сбора в UTC, наблюдения, `SnapshotMetadata` и `sha256` |
| `AdvisorRequest` | Область, ID запроса, вопрос до 4000 символов и необязательный ID слепка |
| `AdvisorResponse` | Область и корреляция, ссылка на слепок, уровень решения, рекомендация, доказательства, причины ручной проверки |

## Сбор слепка

Области — `crm`, `robots`, `workflows`, `smart_processes`, `permissions`, `analytics`. Проверяй покрытие каждой запрошенной области. Нормализуй только необходимые метаданные и храни безопасный идентификатор источника в `source_ref`. `observed` означает подтверждённое наблюдение в пределах видимости аккаунта. `no_access`, `unsupported` и `error` фиксируют разные причины пробела. Недоступные через транспорт данные можно запросить у администратора как отдельное подтверждение.

Общий диспетчер на канонический портал допускает пять проверенных методов чтения. Их семантика сохраняется при передаче JSON через POST. Batch, произвольные методы и операции записи запрещены. Не отправляй значения полей карточек и персональные данные моделям.

| Метод | Сохраняемые метаданные |
| --- | --- |
| `method.get` | Для каждого метода allowlist имя, `isExisting`, `isAvailable` и scope, если API его вернул |
| `crm.type.list` | `entityTypeId`, название и признаки включённых воронок и стадий смарт-процесса |
| `crm.category.list` | ID типа, ID воронки и название |
| `crm.status.list` | Код справочника, ID стадии, название и порядок |
| `crm.item.fields` | ID типа, код и тип поля, признаки обязательности, множественности и read-only |

`crm.item.fields` вызывается для лидов, сделок, контактов, компаний, предложений, новых счетов и найденных смарт-процессов. Стадии лидов и предложений берутся из `STATUS` и `QUOTE_STATUS`. Для сделок, новых счетов и смарт-процессов используются коды справочников по видимым воронкам. Если API вернул `next`, следующий запрос использует `start`. При ошибке сохраняются ранее нормализованные страницы и наблюдение о пробеле. [Метаданные полей](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-fields.html) · [Справочники стадий](https://apidocs.bitrix24.ru/tutorials/crm/how-to-get-lists/how-to-get-elements-by-stage-filter.html)

`method.get` описывает доступность в пределах scope вебхука. Права пользователя проверяются при вызове каждого метода. `bizproc.robot.list` перечисляет регистрации приложения, поэтому сборщик фиксирует `unsupported` для штатных роботов на стадиях. Фаза 2 также помечает пробелы для матрицы прав, бизнес-процессов и аналитики. [Доступность методов](https://apidocs.bitrix24.ru/api-reference/common/system/method-get.html) · [Реестр роботов приложения](https://apidocs.bitrix24.ru/api-reference/bizproc/bizproc-robot/bizproc-robot-list.html)

`sha256` считается от UTF-8 JSON с версией канонизации `1`, без пробелов, с сортировкой ключей и каждой коллекции по каноническому JSON её записей. Хэш включает метаданные и наблюдения, в том числе коды неполноты. Так одинаковое содержимое можно сравнивать независимо от порядка выдачи, области хранения, времени, ID слепка и запроса. `metadata` и `sha256` допускают совместное отсутствие для слепков каркаса. Для слепков фазы 2 хэш проверяется при валидации DTO.

`verify_snapshot` и `advisor_pilot --snapshot` принимают экспорт `PortalSnapshot` с `metadata` и валидным `sha256`. Отчёт сверки содержит структуру, счётчики наблюдений, пробелы и статус ручной проверки `pending`. Хэш подтверждает целостность метаданных и наблюдений, а принадлежность экспорта согласованному порталу подтверждает оператор.

Лимит приложения — максимум 2 req/s на портал. Диспетчер по каноническому имени хоста начинает запросы с интервалом ≥ 500 мс по монотонным часам. Клиенты одного процесса делят лимитер между учётными записями, страницами и повторами. На запрос предусмотрены три попытки с ожиданиями 1 и 2 секунды при таймауте или ограничении интенсивности. Для ограничения интенсивности учитывается `Retry-After` в секундах или формате HTTP-date. При ожидании свыше 60 секунд или исчерпании попыток фиксируется пробел. CLI разрешает один живой сбор на хост в общем рабочем каталоге. [Лимиты REST API](https://apidocs.bitrix24.ru/settings/performance/limits.html)

## Консультация и доказательства

`Fragment` хранит `fragment_id`, HTTPS `url` официальной справки или REST-документации Битрикс24, `checked_at` в UTC, `revision_or_hash`, `snippet`, области аудита, применимые разделы, сущности и тарифы. Пустые списки сущностей и тарифов означают отсутствие ограничения у конкретного фрагмента. Если ограничение задано, советник требует подтверждённое приложением значение. Возраст проверяется от времени запроса, включая границу 30 дней по умолчанию. Источники с будущим временем проверки исключаются.

`KnowledgeBase` хранит корпус в SQLite по паре `tenant_id` + `portal_id`. Импорт целиком заменяет корпус указанной области одной транзакцией. Ревизия векторного индекса включает формат, URL провайдера и модель эмбеддингов. Поиск ведётся по области, применимости, свежести, совпадениям слов и косинусной близости. Если подходящие векторы отсутствуют или провайдер недоступен, остаётся поиск по словам. Чтобы восстановить векторный поиск после смены модели, импортируй корпус повторно.

`Advisor.run` принимает доверенную область, необязательный слепок и подготовленный приложением обезличенный `public_question` для сетевого вызова. Поля корреляции берутся из запроса. При заданном `snapshot_id` слепок должен совпасть по ID и по обоим полям области. Неизвестная область, небезопасный вход, отсутствие свежей документации и несовместимые значения одного редакторского `claim_key` ведут к `undetermined` и `need_human=true`. Для неструктурированных противоречий модель может вернуть причины проверки в черновике.

Для `revision_or_hash` в стартовом корпусе используется префикс `sha256:` и SHA-256 от UTF-8 текста `snippet`. Поиск пилота без векторов требует совпадения полных слов и возвращает кандидатов в порядке оценки. `missing_sources` проверяет покрытие областей первыми 12 применимыми фрагментами для объединения областей fast и локального маршрута.

Проверка `visibility_gap` использует те же области. Если в рабочей формулировке явно названы стандартные типы CRM или приложение передало подтверждённый `entity`, советник объединяет эти цели. Для `entity` поддерживаются ID типов 1, 2, 3, 4, 7, 31 в виде строк и имена `lead`, `deal`, `contact`, `company`, `quote`, `smart_invoice`. Неизвестное значение `entity` или отсутствие распознанных целей оставляет проверку всей области.

При наличии в слепке типизированных наблюдений CRM советник определяет их тип по `source_ref` полей, воронок и справочников стадий. Для известных целей исключаются наблюдения по остальным типам. Среди первых 50 подтверждённых наблюдений после фильтрации требуется покрытие каждой нужной области и каждого выбранного типа CRM. Любой статус кроме `observed` среди оставшихся наблюдений добавляет `visibility_gap`, включая ошибки источников без распознанного типа и ограничения по роботам, бизнес-процессам, правам, аналитике и смарт-процессам. Слепки с наблюдениями только на уровне области проверяются по областям.

Коды `unknown_area`, `unsafe_input`, `missing_sources` и `conflicting_sources` блокируют сетевой вызов smart. При `visibility_gap` или `missing_snapshot` и достаточном покрытии справкой smart может сформировать условный `native` или `extension`. Советник сохраняет коды пробелов, помечает настройки условными и выставляет `need_human=true`. В `review_reasons` он объединяет пункты ручной сверки по затронутым областям и уточнения модели. Отклонение черновика добавляет код проверки доказательств к уже имеющимся кодам. `AdvisorResponse` уровня `undetermined` возвращает пустые списки доказательств, поэтому по одним итоговым ссылкам пилота нельзя восстановить кандидатов поиска.

`AdvisorEngine.run` принимает `AdvisorRequest`, загружает указанный слепок из той же SQLite, что и корпус, запускает советник и возвращает `AdvisorRun` после успешной записи истории. Поиск слепка использует точную тройку `tenant_id`, `portal_id`, `snapshot_id`. При отсутствии ID или совпадения ответ содержит `snapshot_id=null`, явную оговорку об условности и код `missing_snapshot`.

`Draft` содержит уровень решения, текст рекомендации, возможный `native_gap`, идентификаторы фрагментов, порядковые номера наблюдений и причины проверки. Код проверяет принадлежность ID, покрытие документацией всех нужных областей и наличие ссылок на наблюдения по каждой области, где они переданы, затем собирает `AdvisorResponse` из исходных объектов. Поля `revision` и `excerpt` ответа соответствуют `revision_or_hash` и `snippet` фрагмента. Для `native` нужна официальная справка по каждой области. Для `extension` указанное требование должно совпасть с курируемым `native_gap` одного из процитированных фрагментов. URL возвращаются в структурированных доказательствах. Проверка принадлежности подтверждает происхождение материала. Смысловое соответствие свободного текста формулировкам источника проверяется на размеченных кейсах.

Для условного `native` или `extension` без переданных наблюдений допустим пустой `observation_ids`. DTO требует ручной проверки для рекомендации без наблюдений. Указанные ID всегда должны входить в переданный набор, включая индексы наблюдений от нуля. URL и ссылки в тексте рекомендации и её пунктах проверки ведут к `undetermined` с кодом `unsupported_conclusion`, даже если черновик прошёл валидацию DTO.

`AdvisorRun` содержит проверенный ответ, версии обоих промптов, стабильные `review_codes` и `Execution` для маршрутизации, рекомендации и поискового эмбеддинга, если его запрашивали. Шлюз разделяет роли fast, smart и embedding, использует JSON object mode для чата и строго валидирует DTO. `Execution` содержит `mode`, `fallback_reason`, `tokens_in`, `tokens_out` и `cost_rub_e8`. Режимы — `llm`, `deterministic`, `fallback`. Для детерминированного вызова счётчики и стоимость равны нулю. В режиме fallback известный расход сохраняется даже при отклонённом ответе модели.

## Прикладные кейс-паки

Файлы загружаются в лексикографическом порядке имён. Интерфейс сохраняет этот порядок в списке выбора.

Приложение читает JSON из `docs/cases/` через DTO `CasePack` и `CaseStep` из `apps/advisor_ui_support.py`. Имя файла совпадает с `case_id`. Паспорт содержит название, бизнес-контур, боль, дорогие ошибки и оценку штатной архитектуры. Упорядоченные шаги имеют уникальные ID и содержат вопрос до 4000 символов, ожидаемые области, ссылки на фрагменты корпуса, проект штатного решения и пункты ручной сверки. Ссылки уникальны внутри шага и покрывают его ожидаемые области.

Пакет запускает шаги последовательно через `AdvisorEngine` в одной области, с одним выбранным слепком или без него. Каждый запрос получает свой UUID и транзакцию истории. Перед сетевым режимом приложение требует подтверждение расхода на пакет. Ожидаемые области и фрагменты описывают редакторский план. Поиск и проверка доказательств по-прежнему выполняются советником для каждого вопроса. Отчёт Markdown собирается в сессии из всех завершённых шагов, редакторского плана и телеметрии. При прерывании сохраняются ранее записанные шаги истории.

## SQLite WAL

[infra/schema.sql](../infra/schema.sql) создаёт `portal_snapshots`, `advisor_runs`, `advisor_run_telemetry` и `knowledge_fragments`. Схема использует `STRICT`, JSON-колонки и внешние ключи с полями области. JSON проверяй по DTO до записи и при чтении. Во всех операциях фильтруй область. Храни файл на локальном диске, проверяй `journal_mode=wal` и включай `foreign_keys=ON` и `busy_timeout=5000` при каждом подключении.

`SnapshotStore` проверяет настройки соединения, валидирует DTO при записи и чтении и ищет слепок по тенанту, порталу и ID. Хэш хранится в JSON слепка, существующий DDL совместим с новыми записями.

`AdvisorHistory` пишет обе строки завершённого запуска одной транзакцией. `advisor_runs.response_json` хранит минимальный `RunOutcome` с корреляцией, ID слепка, уровнем решения и кодами проверки. Вопрос, рекомендация, свободные причины модели, цитаты и наблюдения остаются вне истории. Свободной причине модели соответствует код `model_review`. Версии промптов сохраняются отдельно. `AdvisorHistory.get(scope, request_id)` возвращает `RunRecord` вместе с проверенной телеметрией. Повторная запись того же ID в одной области отклоняется уникальным ключом. Запись выполняется после вычисления, поэтому повторный вызов может снова обратиться к модели до отклонения.

`RunTelemetry` содержит время завершения в UTC, монотонную длительность от входа до записи в мс без самой транзакции и расход стадий. Общий режим `fallback` означает fallback хотя бы одной стадии. Иначе режим `llm` требует сетевой стадии, а `deterministic` означает полностью локальное выполнение. При подменённом транспорте режим описывает ветку шлюза.

`AdvisorHistory.list_completed(scope)` возвращает проверенные `RunRecord` выбранной области от новых к старым. `RunSummary.from_records` считает долю штатных решений через число `native`, включая условные планы с кодом `missing_snapshot` или `visibility_gap`. Неизвестные расходы считаются отдельно от суммы известных.

`DocumentationEvidence.title` — необязательный заголовок для отображения. База знаний берёт его из первого раздела фрагмента. Ранее сформированные DTO без заголовка остаются допустимыми.

`cost_rub_e8` — целое количество стомиллионных долей рубля после округления `Decimal` до восьми знаков по ROUND_HALF_EVEN. Тарифы задаются в рублях за миллион входных и выходных токенов. Итог равен сумме стадий, включая поисковый эмбеддинг при наличии. Неизвестный расход любой стадии или переполнение дают `None` в DTO и `NULL` в SQLite.
