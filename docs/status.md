# Состояние b24-native-advisor

> Обновлять на месте после проверок. Объём 80–130 физических строк.

## Фаза и цель

- Фазы 1–4 завершены в локальном контуре. Прикладной пилот доступен из CLI и локального веб-интерфейса.
- Советник сопоставляет read-only слепок портала с официальной документацией Битрикс24.
- Приоритет получают штатные средства CRM, смарт-процессов, автоматизации, прав и аналитики.
- Расширение требует подтверждённого разрыва в штатных возможностях.
- Изменения на портале выполняет администратор.

## Компоненты

- `core/config.py` загружает настройки вебхука, моделей и порога актуальности.
- `core/contracts.py` описывает DTO запросов, слепка и ответа советника.
- `core/storage.py` и `infra/schema.sql` обеспечивают локальное хранение SQLite WAL.
- `core/advisor_history.py` сохраняет минимальные итоги и телеметрию завершённых запросов.
- `core/llm.py` реализует OpenAI-совместимый шлюз чата и эмбеддингов.
- `core/knowledge.py` валидирует, индексирует и ищет фрагменты документации.
- `core/prompts.py` загружает версионированные шаблоны и правила исполнения из реестра.
- `modules/portal_audit/` собирает метаданные и отмечает пределы видимости портала.
- `modules/advisor/service.py` маршрутизирует запрос и проверяет доказательства рекомендации.
- `modules/advisor/engine.py` привязывает сохранённый слепок, запускает советник и пишет историю.
- `ops/runners/collect_snapshot.py` запускает синтетический или явно запрошенный живой аудит.
- `ops/runners/verify_snapshot.py` проверяет хэш экспорта и готовит чек-лист сверки с интерфейсом.
- `ops/runners/knowledge_index.py` импортирует корпус и запускает синтетический прогон.
- `ops/runners/advisor_benchmark.py` запускает сквозной smoke и сравнение с разметкой.
- `ops/runners/advisor_pilot.py` выполняет четыре прикладных запроса на синтетике или экспорте.
- `docs/knowledge/bitrix24.json` содержит 50 фрагментов официальной справки и REST-документации.
- `docs/cases/01_lead_leak_and_dormant_base.json` связывает распределение заявок, контроль первого ответа и реактивацию базы.
- `docs/cases/02_contract_approval_bottleneck.json` связывает генерацию договора, согласование и передачу сделки в работу после оплаты.
- `docs/cases/03_production_and_claims_spa.json` связывает продажу со смарт-процессами закупок, производства и рекламаций и описывает контроль связей и сроков.
- `docs/cases/04_permissions_and_crm_analytics.json` связывает изоляцию направлений, роли и запрет экспорта со сверкой штатной CRM-аналитики.
- `apps/advisor_ui.py` открывает консультацию и историю в Streamlit на `127.0.0.1:8501`.
- `apps/advisor_ui_support.py` валидирует кейс-паки, выполняет их через движок и собирает отчёт Markdown.

## Слепок и хранение

- Сборщик читает метаданные полей, типов, воронок и стадий через пять разрешённых REST-методов.
- Поля читаются для лидов, сделок, контактов, компаний, предложений, новых счетов и видимых смарт-процессов.
- `method.get` сообщает доступность метода в scope. Права пользователя проверяются при предметном вызове.
- Статусы `no_access`, `unsupported` и `error` фиксируют разные причины пробела.
- При ошибке на следующей странице сборщик сохраняет уже проверенные страницы.
- Диспетчер выдерживает интервал не менее 500 мс между запросами к одному хосту.
- При таймауте или ограничении интенсивности доступны до трёх попыток. Учитывается `Retry-After`.
- Привязка IP меняет TCP-адрес, сохраняя имя портала для проверки TLS и SNI.
- Слепки и корпус разделены по `tenant_id` и `portal_id`.
- Соединения SQLite проверяют WAL, `foreign_keys=ON` и `busy_timeout=5000`.
- Слепок включает SHA-256 канонизированных метаданных и наблюдений.
- Живые слепки и рабочие БД по умолчанию хранятся в `.local/`.
- При отсутствии доступного слепка ответ явно помечает выводы о настройках условными.
- Итог и телеметрия записываются одной транзакцией. История поддерживает чтение по ID и список завершённых запусков выбранной области.
- Веб-интерфейс использует `.local/advisor_ui.sqlite3`. Запросы без слепка относятся к области `documentation.invalid` выбранного тенанта.
- История хранит версии промптов, длительность, токены и стоимость стадий, режим и коды проверки.
- Каждый шаг кейса записывается отдельной транзакцией. В сессии UI кнопка скачивания отчёта находится под заголовком карты решений.
- Вопросы, ответы модели и содержимое наблюдений в истории отсутствуют.

## Корпус и доказательства

- Фрагмент содержит HTTPS URL, время проверки в UTC, ревизию или хэш, текст и метаданные применимости.
- Корпус охватывает воронки, туннели, дубли, очереди обращений, повторные продажи, роботов, бизнес-процессы, смарт-процессы, права и аналитику.
- Два фрагмента с `native_gap` описывают асинхронный внешний скоринг и компенсации после частичного сбоя интеграции.
- По умолчанию поиск принимает фрагменты возрастом до 30 дней включительно.
- Фрагменты с будущим временем проверки исключаются.
- Импорт заменяет корпус одной области SQLite-транзакцией.
- Кнопка импорта веб-интерфейса загружает стартовый корпус для выбранной области и использует локальный поиск по словам.
- Ревизия индекса учитывает формат, провайдера и модель эмбеддингов.
- Поиск по словам доступен при отсутствии подходящего векторного индекса.
- Несовместимые значения одного редакторского ключа утверждения требуют ручной проверки.
- Цитаты и наблюдения ответа восстанавливаются по ID из переданных доказательств.
- Для явно названных стандартных типов CRM покрытие проверяется по каждому целевому типу. Ошибки по остальным типам CRM исключаются из расчёта.
- Неизвестный тип источника и ограничения по другим нужным областям учитываются на уровне области.
- Недостаточное покрытие и противоречивые источники блокируют smart и ведут к `undetermined`.
- `visibility_gap` и `missing_snapshot` допускают условный план при свежей документации по всем нужным областям. Чужой слепок исключается.
- Условный план требует ручной проверки. Наблюдения цитируются по каждой области, где они доступны.
- Для `native` требуется официальная справка по каждой нужной области.
- Для `extension` требуется точное совпадение разрыва с редакторским полем процитированного фрагмента.

## Модели

- `FAST_LLM_MODEL` выполняет `advisor.route` версии `1.0.0`.
- `SMART_LLM_MODEL` выполняет `advisor.recommend` версии `1.2.0`. Версии `1.0.0` и `1.1.0` доступны для воспроизведения.
- Для `native` и `extension` промпт требует применимые ID фрагментов и доступных наблюдений. Ссылки в тексте рекомендации запрещены.
- `EMBEDDING_MODEL` векторизует документальные фрагменты и поисковые запросы.
- Чат использует JSON object mode, удаляет внешнее Markdown-ограждение и строго проверяет выходной DTO.
- Шлюз фиксирует режим, причину fallback и известные счётчики токенов.
- Рублёвая стоимость рассчитывается через `Decimal` и возвращается как целое `cost_rub_e8` либо `None`.
- Для сетевого вызова приложение передаёт обезличенный вопрос. Модель получает безопасную проекцию наблюдений.
- Сухой прогон выполняет обе стадии детерминированно и возвращает черновик для ручной проверки.

## Текущие ограничения

- Целевую стадию согласования и её воронку нужно подтвердить в интерфейсе портала.
- Для смарт-процессов администратор подтверждает связи со сделками, поля, права и автоматизацию.
- Ошибка чтения категорий контактов может дать `visibility_gap` для запросов о контактах и запросов с неопределённым типом CRM.
- Эффективные роли, запрет экспорта и доступ к аналитике под руководителями сверяются в интерфейсе портала.
- Код проверяет происхождение доказательств. Проверка смысла свободного текста ограничена размеченными кейсами.
- История содержит завершённые результаты. Повторный расчёт с тем же ID может обратиться к модели до отклонения записи.
- Рублёвая стоимость в веб-интерфейсе рассчитывается по локальному файлу тарифов `B24_UI_PRICES`. Без тарифа расход сетевой стадии неизвестен.
- Повтор прерванного кейса пересчитывает все шаги. Перед повтором история показывает уже завершённые шаги и их расход.

## Следующие шаги

1. Сверить четыре кейс-пака на согласованном портале по чек-листам отчётов. Для третьего проверить связь и таймлайн SPA, фильтр и эскалацию просрочки. Для четвёртого сверить матрицу прав, штатный экспорт и данные отчётов по отделам.
2. При согласованном живом read-only сборе получить актуальный экспорт. В следующем согласованном сетевом замере проверить условные планы smart 1.2.0 по четырём кейсам пилота.
