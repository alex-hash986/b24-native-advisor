# Локальный запуск и проверки

Для аудита нужны Python 3.11+ и SQLite 3.37+ с поддержкой JSON. Запускай команды из корня проекта.

## Подготовка на Windows

```powershell
py -3.14 -m venv .venv
& .\.venv\Scripts\python.exe -m pip install --upgrade pip
& .\.venv\Scripts\python.exe -m pip install "pydantic>=2,<3" "python-dotenv>=1,<2" "pytest>=8,<10" "ruff>=0.11,<1" "mypy>=1.15,<3"
Copy-Item .env.example .env
```

Копируй шаблон при создании локальной конфигурации. Для будущих слушателей и пробросов оставляй `B24_NATIVE_ADVISOR_HOST=127.0.0.1`. SQLite размещай на локальном диске. Храни `.env`, БД и живые слепки вне системы контроля версий.

## Проверки и синтетический сбор

```powershell
New-Item -ItemType Directory -Force .local | Out-Null
$env:PYTEST_DISABLE_PLUGIN_AUTOLOAD = '1'
& .\.venv\Scripts\python.exe -m pytest --basetemp .local/pytest_tmp
& .\.venv\Scripts\python.exe -m ruff check .
& .\.venv\Scripts\python.exe -m mypy .
& .\.venv\Scripts\python.exe -m ops.runners.collect_snapshot --dry-run
```

Можно использовать установленное окружение, заменив путь к интерпретатору на `py -3.14`. При `WinError 5` в системном временном каталоге используй указанный `--basetemp .local/pytest_tmp`. Если доступ к ранее созданному каталогу уже потерян, выбери новый путь внутри `.local/` через `--basetemp (Join-Path .local ([guid]::NewGuid().ToString()))`.

`--dry-run` читает синтетические ответы и сохраняет их в `.local/dry-run.sqlite3` и отдельный `.local/snapshot-<request_id>.json`. Тесты подменяют сетевой транспорт и проверяют изоляцию данных, WAL, повторы, TLS-параметры и неполный сбор.

## Веб-интерфейс советника

Установи зависимость группы `ui` в то же окружение, где установлены основные зависимости. Из корня проекта выполни:

```powershell
py -3.14 -m pip install "streamlit>=1.67,<2"
py -3.14 -m streamlit run apps/advisor_ui.py
```

Открой [локальное приложение](http://127.0.0.1:8501). Приложение использует `.local/advisor_ui.sqlite3`.

1. Выбери сухой прогон или настроенного провайдера и, при наличии, экспорт слепка. Список включает JSON из корня `.local/` с валидным хэшем и совпадающим `B24_TENANT_ID`. Слепок используется локально. Без слепка корпус и история относятся к отдельной области `documentation.invalid`.
2. Нажми «Загрузить / обновить корпус» при первом использовании каждой области и после обновления `docs/knowledge/bitrix24.json`. Импорт использует поиск по словам и выполняется локально в обоих режимах. Возраст источников проверяется на момент запроса.
3. Выбери один из четырёх демо-кейсов или введи свою задачу и нажми «Подобрать штатное решение». В карточке доступны рекомендации, пункты ручной проверки, источники и телеметрия. Сухой прогон сохраняет детерминированный результат для ручной проверки с расходом 0 ₽.
4. На вкладке «История и экономика» выбери нужную область через слепок в боковой панели. Таблица показывает завершённые запуски со временем, режимом и вердиктом. Доля штатных и условных решений включает принятые `native`. Условные планы выделены в счётчике. Запуски с неизвестной стоимостью отмечены отдельно.

Для сетевого режима задай `LLM_BASE_URL`, `FAST_LLM_MODEL`, `SMART_LLM_MODEL` и при необходимости `LLM_API_KEY`. Перед отправкой подтверди, что задача обезличена. Ключ отображается только как статус наличия. Чтобы видеть расчётный расход, задай переменную процесса `B24_UI_PRICES` с путём к JSON тарифов в формате `advisor_pilot --prices`. Если тарифы неизвестны, интерфейс показывает только доступную часть суммарного расхода. Приложение не запускает аудит портала.

### Прикладные кейс-паки

1. В боковой панели выбери режим и слепок или вариант «Без слепка портала». Загрузи обновлённый корпус в выбранную область.
2. Открой вкладку «Прикладные кейс-паки», выбери пакет и раскрой его паспорт. Пакеты отображаются в порядке имён файлов.
   - [Кейс 1 · Утечка входящих лидов и мёртвая база](cases/01_lead_leak_and_dormant_base.json) связывает распределение обращений, контроль первого ответа и реактивацию базы.
   - [Кейс 2 · Договорной паралич и бесконечные согласования](cases/02_contract_approval_bottleneck.json) связывает генерацию договора, согласование в БП и передачу сделки в работу после оплаты счёта.
   - [Кейс 3 · Производство, закупки и рекламации внутри одной воронки продаж](cases/03_production_and_claims_spa.json) связывает раздельные смарт-процессы, передачу заказа из сделки и контроль связей и сроков.
   - [Кейс 4 · Бардак в правах, утечка базы и непрозрачная аналитика](cases/04_permissions_and_crm_analytics.json) связывает изоляцию филиалов и направлений, запрет экспорта по ролям и сверку штатной отчётности под руководителями отделов.
3. Нажми «Запустить разбор кейса». В живом режиме сначала подтверди сетевой расчёт и расход по всему пакету. Отправляются подготовленные вопросы из кейса и безопасная проекция доказательств. Запросы к порталу в этом режиме отсутствуют. Сухой прогон выполняется локально за 0 ₽.
4. Кнопка «Скачать Markdown-отчёт» появляется под заголовком карты решений. Ниже можно просмотреть отчёт. План по справке требует ручной сверки. Ссылки кейса и цитаты итоговых выводов подписаны отдельно. По каждому шагу видны режим, задержка, токены и стоимость. При неизвестных тарифах указан известный расход и число шагов без оценки.

История хранит каждый завершённый шаг отдельно. Если пакет прервался, сверь историю и расход перед повторным запуском: повтор выполняет все шаги заново. Полный отчёт доступен для скачивания в текущей сессии и сбрасывается при смене кейса, области, слепка или режима.

## Живой read-only аудит

1. Согласуй портал и учётную запись с минимальными правами на чтение нужных объектов CRM. Входящему вебхуку нужен scope `crm`.
2. Заполни `BITRIX24_WEBHOOK_URL` в `.env` корневым адресом вебхука вида `https://portal.example/rest/1/<token>/`.
3. При необходимости укажи `B24_TENANT_ID` (по умолчанию `local`) и `SQLITE_PATH` (по умолчанию `.local/advisor.sqlite3`). ID портала берётся из имени хоста вебхука. Для отдельной конфигурации передай `--env-file`.
4. При нестабильном DNS укажи проверенный адрес в `BITRIX24_PINNED_IP`. Поддерживаются IPv4 и IPv6. IP используется для TCP-соединения, имя портала остаётся в HTTP Host и в проверке TLS и SNI.
5. Запусти раннер из одного согласованного рабочего каталога для каждого портала. Блокировка в `.local/dispatchers/` координирует процессы CLI с общим рабочим каталогом.

```powershell
& .\.venv\Scripts\python.exe -m ops.runners.collect_snapshot --live
```

По умолчанию JSON назван по ID запроса и сохранён в `.local/`. `--output` принимает путь к новому JSON-файлу на файловой системе с поддержкой жёстких ссылок. Относительные пути считаются от рабочего каталога. При успехе раннер печатает ID слепка, хэш и имя файла. Успешное сохранение допускает неполный слепок. Проверь `observations` и источники с `no_access`, `unsupported` и `error`.

JSON публикуется из временного файла целиком. Если запись в SQLite возвращает ошибку, раннер удаляет опубликованный JSON. При принудительном прерывании между публикацией JSON и записью в БД сверь `snapshot_id` в обоих местах. Для согласованной копии работающей БД используй SQLite backup и проверь восстановление на отдельном файле.

### Сверка с интерфейсом портала

```powershell
py -3.14 -m ops.runners.verify_snapshot .local/snapshot-<request_id>.json --output .local/ui-review.json
```

Подставь имя JSON из вывода сборщика и выбери новое имя отчёта. Скрипт проверяет DTO и SHA-256, выписывает пробелы и формирует список для ручной сверки. Он читает только локальный файл и не обращается к порталу или SQLite. Храни отчёт в `.local/`, поскольку он включает названия настроек.

1. Сверяй ближайшую к времени сбора конфигурацию и фиксируй роль вебхука и роль, под которой открыт интерфейс. Отдельно отметь различия видимости двух ролей.
2. Сопоставь воронки сделок, порядок стадий и настройки полей с CRM. Сверь список смарт-процессов, включённые воронки и стадии. Для полей сравнивай код, тип и обязательность там, где эти признаки доступны в интерфейсе.
3. Открой настройки CRM-формы, роботов и ролей для сценариев ниже в режиме просмотра. Не сохраняй настройки, не запускай процессы, не создавай тестовые карточки на рабочем портале.
4. Сохрани результаты в `.local/` с ID и хэшем слепка, временем сверки, областью, ссылкой на источник без секретов и итогом по пункту (`match`, `difference`, `not_visible`, `not_checked`). Для расхождения запиши, что видно в REST и интерфейсе, и отдельно предполагаемую причину. Не включай содержимое карточек, имена сотрудников и токены.

Пустой набор с `observed` означает отсутствие записей в пределах видимости вызова. `method.get` показывает scope метода. Матрица ролей и настройки штатных роботов проверяются в интерфейсе. `ui_verification=pending` означает подготовленную сверку.

Публичные источники для корпуса описывают роботов, бизнес-процессы, смарт-процессы и ограничения REST. [Роботы и триггеры](https://helpdesk.bitrix24.ru/open/24633726/) · [Бизнес-процессы](https://helpdesk.bitrix24.ru/open/21290220/) · [Смарт-процессы](https://helpdesk.bitrix24.ru/open/18913884/) · [Лимиты REST](https://apidocs.bitrix24.ru/settings/performance/limits.html)

## База знаний и шлюз моделей

```powershell
& .\.venv\Scripts\python.exe -m ops.runners.knowledge_index --dry-run
```

Сухой прогон загружает синтетические фрагменты, проверяет локальный поиск и выполняет обе стадии советника. Он использует отдельную БД `.local/knowledge-dry-run.sqlite3`, фиксированное время проверки и нулевые счётчики расхода. Ожидаемый итог — два найденных фрагмента и `undetermined`, поскольку локальная заглушка передаёт решение на ручную проверку. Для проверки другого набора передай `--corpus <путь>`.

В корпусе Битрикс24 50 фрагментов. Они охватывают воронки и туннели сделок, обязательные поля и дубли, реквизиты и модификаторы шаблонов документов, очереди форм и Открытых линий, повторные продажи, роботов и триггеры, согласования в БП, смарт-процессы, фильтр по связям, копирование таймлайна через Маркетплейс, роли, разрешение на экспорт и аналитику. Отдельные фрагменты описывают внешний скоринг и компенсации при частичном сбое интеграции. [Корпус Битрикс24](knowledge/bitrix24.json)

При пополнении корпуса сверь страницу с фрагментом, обнови время проверки в UTC и запиши SHA-256 текста `snippet`. Назначай один `claim_key` только одному утверждению с согласованным `claim_value`. Используй `native_gap` для конкретного документированного требования к расширению. Для ограниченной применимости укажи сущности и тарифы. По умолчанию используется порог `B24_DOCS_MAX_AGE_DAYS=30`.

После обновления корпуса повтори импорт для нужной области. В веб-интерфейсе нажми «Загрузить / обновить корпус» для каждого используемого портала и отдельно для режима без слепка.

```powershell
& .\.venv\Scripts\python.exe -m ops.runners.knowledge_index --index --corpus docs/knowledge/bitrix24.json --portal-id portal.example
```

Импорт целиком заменяет корпус указанного портала в тенанте `B24_TENANT_ID`. Он использует `SQLITE_PATH` и не обращается к порталу. Загружай подготовленный корпус официальных источников. Для индексации с эмбеддингами задай `LLM_BASE_URL` (включая `/v1`, если его ожидает провайдер), `LLM_API_KEY` при необходимости и `EMBEDDING_MODEL`. Такой импорт отправляет провайдеру текст фрагментов и может быть платным. Без настроенной модели работает поиск по словам. После смены провайдера или модели повтори импорт. Число `embedded` показывает, сколько вызовов индексации получили валидный ответ.

Для интеграции настрой `FAST_LLM_MODEL` и `SMART_LLM_MODEL`. Передай в `AdvisorEngine(Advisor(gateway, knowledge, prompts)).run` запрос с доверенной областью, новым `request_id` и ID сохранённого слепка при наличии. Для сетевого вызова подготовь `public_question` без секретов, персональных данных и содержимого карточек. При необходимости передай подтверждённые `entity` и `tariff`. Для моделей и порога актуальности переменные процесса имеют приоритет над `.env`. Для расчёта стоимости передай `prices` при создании `LLMGateway` с тарифами в рублях за миллион токенов. Без тарифа расход в рублях неизвестен. История читается через `engine.history.get(scope, request_id)`.

## Прикладной пилот

| Кейс | Штатный вариант для проверки | Что подтвердить в интерфейсе |
| --- | --- | --- |
| `routing` | Очередь ответственных в CRM-форме | Режим CRM, тип создаваемого элемента, очередь формы и настройки рабочего времени. [Справка](https://helpdesk.bitrix24.ru/open/27516124/) |

| `access` | Роль CRM с правом на свои сделки в нужной воронке | Уровни доступа по операциям, назначенные роли и права на соседние воронки. [Справка](https://helpdesk.bitrix24.ru/open/23240636/) |
| `smart-process` | Смарт-процесс для отдельного цикла рекламаций, сделка для этапов продажи | Поля, стадии, связь со сделкой и доступность опций на тарифе. [Справка](https://helpdesk.bitrix24.ru/open/18913884/) |

```powershell
py -3.14 -m ops.runners.advisor_pilot --dry-run
py -3.14 -m ops.runners.advisor_pilot --dry-run --snapshot .local/snapshot-<request_id>.json
py -3.14 -m ops.runners.advisor_pilot --provider --snapshot .local/snapshot-<request_id>.json
```

Без `--snapshot` используется синтетический слепок. Раннер загружает слепок и корпус в отдельную временную SQLite в `.local/`. JSON-вывод с итогами, ссылками и телеметрией стадий можно сохранить там же. Сухой прогон воспроизводит поиск на последнюю дату проверки фрагментов и возвращает `undetermined`. Для кейсов с роботами и ролями ожидается `visibility_gap`. Сверяй качество живого ответа с таблицей и реальными настройками.

`--provider` использует текущую свежесть корпуса и настройки моделей из `.env` или `--env-file`. Ключ зависит от провайдера. Передаются четыре фиксированных обезличенных вопроса и безопасная проекция доказательств. Индекс строится локально без сетевых эмбеддингов. При сбое шлюза раннер показывает `fallback` и возвращает код 1. При пробелах fast-стадия может выполниться, а smart-стадия останется детерминированной. Для оценки стоимости передай `--prices` с JSON-объектом по именам моделей и полями `input_per_million_rub` и `output_per_million_rub`. Без тарифа или данных об использовании сетевой расход может быть `null`.

### Проверка покрытия и ручная сверка

Сухой пилот подтвердил хэш синтетического экспорта и привязку к нему четырёх кейсов. Все результаты потребовали ручной проверки. Для роботов и ролей зафиксирован `visibility_gap`. Расход — 0 ₽.

| Кейс | Что сверить в интерфейсе портала |
| --- | --- |
| `routing` | CRM-режим, настройки формы, стартовую стадию, порядок ответственных и учёт рабочего времени. |
| `stage-task` | Целевую воронку и стадию, робота, исполнителя, срок и условия запуска, включая возврат на стадию. |
| `access` | Назначения ролей, доступ по воронкам и итоговые права по операциям при пересечении ролей. |
| `smart-process` | Настройки типа, обязательные поля, категории, стадии и связь со сделкой. |

При сбое шлюза проверь доступность настроенного endpoint и наличие выбранных моделей. При частичном сборе проверь коды наблюдений и состояние ручной сверки. Экспорты, настройки провайдера и результаты живых замеров храни в локальном рабочем контуре.

### Интерпретация результатов с `advisor.recommend@1.2.0`

В сетевом режиме `unknown_area`, `unsafe_input`, `missing_sources` и `conflicting_sources` оставляют smart детерминированной и дают `undetermined`. При `visibility_gap` или `missing_snapshot` smart может потребовать оплаты, если свежая применимая документация покрывает все области. Условный `native` или документально подтверждённый `extension` помечается `need_human=true`. Сверь настройки в интерфейсе по `review_reasons` до применения плана. `review_codes` сохраняет причину пробела и, при отклонении черновика, причину отклонения.

## Сквозной smoke и бенчмарк

```powershell
py -3.14 -m ops.runners.advisor_benchmark --dry-run
```

Раннер готовит изолированную временную БД в `.local/` и очищает её по завершении. Он читает размеченные кейсы из `ops/fixtures/advisor_cases.json`, использует фиксированное время, синтетические слепки, локальные ответы транспорта моделей и нулевые тарифы. Отдельный smoke-кейс использует детерминированные ветки советника с запретом вызова транспорта. Метки `llm` и `fallback` в остальных кейсах показывают ветки шлюза. Сетевых запросов нет. Условные ответы входят в число эскалаций. Кейс расширения использует синтетическую редакторскую отметку о разрыве для внешнего протокола. Проверка качества сравнивает итоговые уровни, причины, доказательства и формулировки с разметкой. Значения характеризуют локальный тракт с подменённым транспортом. Семантика произвольных ответов модели, качество живого аудита и задержки провайдера требуют отдельных замеров.
